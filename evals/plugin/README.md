# Plugin Eval Suite

End-to-end checks that run the skills through Claude Code and grade what they produce. Each case is a folder here (`prompt.md`, `case.yaml`, `setup.sh`, `graders/*.md`), and two runners read the same folders:

- **The harness** (`evals/harness/`) runs on Windows, macOS and Linux through a headless Claude Code session, and is the default:
  ```bash
  bin/construction-python evals/harness/run.py --tag smoke --runs 1
  ```
  See the [harness README](../harness/README.md) for requirements (on Windows, the native Claude Code install), options, and how runs are confined.
- **`claude plugin eval`** runs on macOS, Linux and WSL2 inside Claude Code's own sandbox, with its HTML report and with/without-plugin comparison:
  ```bash
  claude plugin eval . --tag smoke --scaffold --allow-tools Bash Write Edit
  ```
  `--scaffold` lets each case copy the sample project into its workspace and link the toolkit's Python environment; `--allow-tools Bash Write Edit` lets the skills run their scripts and write files; add `--runs 1 --ablation none` for a quick single pass. The sandbox needs `bubblewrap` and `socat` on Linux (`sudo apt install bubblewrap socat`) and is not available on native Windows. Results go to `evals/plugin/results/<timestamp>/`. The first run builds the toolkit's Python environment once in `.eval-home/` at the plugin root (about a minute, needs internet); eval runs themselves have no network.

Harness-only additions to a case (Python checks for xlsx and docx deliverables) live in `harness.yaml` and `checks/`, which `claude plugin eval` ignores. Under either runner, use a stronger judge for `submittal-review` (`--judge-model sonnet`): its final message is a long findings table, and the default judge model sometimes fails findings that are plainly there.

## Tiers

### Smoke (`--tag smoke`) — included

A small synthetic project in `_fixtures/sample-project/`, generated by `_fixtures/make_fixtures.py`: a 4-sheet drawing set (A-201's bookmark is deliberately wrong) and a 2-section project manual. Through the harness on Sonnet, a single pass of the five smoke cases takes about twenty minutes and costs about $9 (from under $1 for project-setup to about $4 for submittal-review). `submittal-review-foodservice` is tagged `large-pdf`, not `smoke`.

| Case | Checks |
|---|---|
| `project-setup` | Context appended to `CLAUDE.md`; no AgentCM files created |
| `sheet-splitter` | Sheets split and named from the printed title block; index next to the sheets; nothing in `.construction/index/` |
| `spec-splitter` | Section PDFs produced; text in `.construction/skills/spec_text/` |
| `submittal-log-generator` | Runs spec-splitter itself; `Submittal_Log.xlsx` produced; items from both sections |
| `submittal-review` | Lab casework shop drawings with four planted defects (sink cutout vs. fixture schedule, accessible station height, in-wall brackets "by others", a missing elevation); completeness gate passes; accessibility left as an open code question; return-to-sub suggested, never approved. Fixture: `_fixtures/make_submittal_fixture.py` |
| `submittal-review-foodservice` | A 366-page foodservice product data package (with scanned pages) against the equipment and electrical connection schedules: a scheduled item missing, a condensing-unit voltage on page 15, a short hood on page 206, an unscheduled extra item; a health-department question left open. Tagged `large-pdf`, not `smoke`: it takes longer. Fixture: `_fixtures/make_foodservice_fixture.py` |

### Real documents (`--tag real`)

Cases built from the plans and specifications of Sanibel Fire and Rescue Station 172. The documents are too large for the repository, so they are downloaded separately and placed under `evals/test_docs/SANIBEL FIRE AND RESCUE STATION 172/` (see [Running Evals](../../docs/RUNNING_EVALS.md#get-test-documents)); `_fixtures/sanibel/make_fixtures.py` then derives small fixtures from them (single sheets, the 8-sheet mechanical set, two trimmed manuals, pre-split flooring sections). Without the downloads these cases are reported as skipped. The expected values come from `_fixtures/sanibel/derive_ground_truth.py`, which reads the same PDFs; its outputs are committed in `_fixtures/sanibel/ground_truth/`.

| Case | Inputs | Checks |
|---|---|---|
| `construction-guide` | Sheet A500 | Known-answer question on door 220: nine values with the sheet cited, the PDF rasterized rather than read directly, a confidence label |
| `schedule-extractor` | Sheet A500 | The door schedule to Excel: 53 doors, width, height, hardware set and material cell-by-cell against the transcription |
| `sheet-splitter-real` | The mechanical set | 8 sheets split and named from their title blocks; the index matches |
| `spec-splitter-real` | A 9-section manual | All sections split; text extracted for each; no POOR ratings |
| `submittal-log-real` | A 4-section manual | Runs spec-splitter itself; log rows cover the Part 1 submittal articles of 09 30 00, 09 65 13 and 09 65 40 |
| `tag-audit-and-takeoff` | Sheet A101 | Flat-file door tag audit: the 16 door numbers printed on the sheet, none invented, no AgentCM calls |
| `code-researcher` | G010, A101, Division 01 excerpts | Offline: facts read from the code summary (FBC 8th Edition 2023, B/R-2/S-2, Type V-B sprinklered), no COMPLIANT / NON-COMPLIANT verdicts, uncertainty stated |
| `pe-review` | Sheet A500 + synthetic Addendum 01 | Door 220: a CONFLICTING finding citing both sources, the addendum governing, severity/type/priority/status |
| `rfi-drafter` | A500, Addendum 01, the firm RFI template | Template mode (firm marker, no generic block), fields filled, facts right, issue registry record escalated |

### Synthetic documents (`--tag synthetic`)

The three skills that need bids or contracts run on generated fixtures in `_fixtures/synthetic/` (see `make_bids.py`, `make_templates.py` and `templates/README.md`): a five-bid flooring package against the real Division 09 sections with planted problems, a firm RFI template, and a 15-article subcontract template with a defective indemnity carve-out and stale example parties. No download needed.

| Case | Checks |
|---|---|
| `bid-tabulator` | Five bidders extracted; totals as stated (including the planted wrong one); alternates with sign; the buried exclusion, budget pricing and allowance captured; the smudged scan value flagged unclear; the scanned bid rasterized |
| `bid-evaluator` | From the tabulated JSON: the silent omission marked SILENT, the math error flagged not corrected, the buried exclusion scored, budget pricing not awardable, the clean low bid recommended, five workbook tabs |
| `subcontract-writer` | From the awarded bid and the template: parties and sum from the bid, `sole negligence` fixed and flagged, stale example parties dropped, no placeholders left, spec sections and bid exclusions carried in |

Through the harness on Sonnet, one run of every case costs about $45 (smoke $9, real $21, synthetic $13, plus about $4 for the large-pdf case); single cases range from under $1 (spec-splitter) to about $6 (subcontract-writer). Note that `claude plugin eval` has no skip convention: without the downloads, the `real` cases fail there rather than skip.

## Known issues

State of the suite as of 2026-10-02. Each case has passed once through the harness on Windows 11 with Sonnet; nothing here has been run on macOS or Linux yet.

**Reliability**

- Every case was verified by a single run. Five cases depend on vision or on a one-vote LLM judge (`construction-guide`, `schedule-extractor`, `tag-audit-and-takeoff`, `pe-review`, `bid-tabulator`), and the default threshold is 1.00, so one grader flap shows as a failed case. Re-run a red case with `--runs 3` (and `--judge-votes 3` for llm graders) before treating it as a regression.
- `subcontract-writer` is the slowest and least stable case: about 18 minutes and $6 when it passes; it once stopped on an API content-filter error after 6 turns (not reproduced) and once ran past a $5 cap while re-verifying its own output. It carries a $10 budget in its `harness.yaml`.
- A full run of all 18 cases costs about $45 on Sonnet and takes well over an hour. Costs are per case in the tables above.

**Platform and runner**

- On Windows the harness needs the native Claude Code install (`claude.exe`); the Agent SDK refuses npm's `claude.cmd` shim. Having both installs makes `claude doctor` warn about it. Shell commands in a Windows run are confined by the harness's policy guard only, not by an OS sandbox (see the [harness README](../harness/README.md)).
- `claude plugin eval` has no skip convention: without the Sanibel downloads, the `real` cases fail there instead of skipping. The scaffold change for the harness (`CONSTRUCTION_EVAL_HARNESS=1` early exit in `_fixtures/prepare-workspace.sh`) and `--sandbox auto` have not been exercised under `claude plugin eval` or on macOS/Linux.
- The `real` cases need the Sanibel downloads (links in `docs/RUNNING_EVALS.md`), about 100 MB. The set holds the architectural, civil, electrical and mechanical sheets only; structural, plumbing, fire protection, technology and landscape sheets are indexed on the cover sheet but not included, which limits `pe-review` to those four disciplines.

**Skills with known defects the cases work around**

- No case asserts an issue-registry record after a `pe-review` review. Since the `issue_manager.py add` command moved into construction-guide (0.5.0), the review does write one (two `ISS-*.json` records in the 2026-10-04 re-run), so the case could grade it.
- `subcontract-writer`'s generator appends its output after the template body when `docx_template_path` is set instead of filling the template; the case does not use that path.
- `bid-evaluator` recommended Sandbar (the image-only bid with a smudged price and no addenda acknowledgement) conditionally over the clean control bid, Gulfshore, in both runs so far (2026-10-02 and 2026-10-04). The skill had no rule for a low bidder with curable defects; SKILL.md 2e now states the conditional-recommendation policy the runs chose, and the check accepts either outcome when the cures are named conditions.
- `bid-tabulator` and `subcontract-writer` each wrote helper scripts and inline Python in their 2026-10-04 runs (text dumps where the skill said "use pdfplumber" with no script for it; JSON assembly with arithmetic assertions; workbook post-processing), and both passed. Since then: `pdf_text.py` and `docx_text.py` exist and are allowlisted, the exporters make the arithmetic checks and render the missing rows, the skills carry a measured Gotchas entry, and the three bid cases fail on a model-written `.py`, on `python -c` or on a heredoc script. The audit measured the same habit in submittal-review, which has no such grader yet.
- `submittal-log-generator` (505 lines) and `subcontract-writer` (531) exceed the SOP's 500-line limit.
- `bid-tabulator`'s workbook lacks the lowest/highest highlighting and the "Base Bid" row its SKILL.md promises; the case grades the per-bid JSON instead. (Allowances, addenda, insurance and a Flags tab are rendered since 2026-10-05.)
- Secondary: `sheet-splitter` does not say how `sheet_index.yaml` follows a rename and a re-run re-adds `page_NNN` entries; `spec-splitter` claims to skip existing sections but overwrites; `submittal-log-generator` merges batch files with `jq`, which may be missing on Windows.

**submittal-review cases: variances from the conventions above** (merged from `feat/submittal-review` on 2026-10-04). Measured 2026-10-03 under `claude plugin eval` with a Sonnet judge (two runs per arm, macOS/Linux): `submittal-review` scored 1.00 with the plugin and 0.78 without it (about $0.71 and 18 turns per run with the plugin); `submittal-review-foodservice` scored 1.00 with the plugin and 0.72 without it (about $1.31 and 44 turns per run with the plugin). Through the harness on Windows with Sonnet, `submittal-review` scored 1.00 at $4.07 and 42 turns on 2026-10-04. `submittal-review-foodservice` through the harness on Windows (Sonnet, three-vote Sonnet judge, 2026-10-04): 1.00 in both of two runs, $3.64 and $4.98, 61 and 59 turns, about 12 minutes each.

| Convention | What the two cases do instead |
|---|---|
| 1. Sanibel basis | Fully invented projects (a science lab, a central kitchen): generated drawings, spec sections and submittals. Proposed amendment: a generated door-hardware submittal reviewed against the real A500 door schedule (53 doors with hardware sets and ratings) and the real 08 71 00 / 08 11 13 / 08 14 16 sections, which the ground truth already covers. |
| 2. Committed ground truth | The planted defects exist only in each generator's docstring and in the grader rubrics; no ground-truth file or defect manifest. |
| 3. Python checks | None. Seven of ten graders are `llm` judges, and the README asks for `--judge-model sonnet` because the default judge flaps. The `review_*.json` records and the `GC Review` workbook could be checked directly. |
| 5. Tools | `Agent` is granted (subagents). |
| 6. Limits | `max_turns: 200`; timeouts 3000 s and 3600 s. |

**Not covered**

- There are no direct script tests yet for the exporters, splitters, `issue_manager.py` or the markup scripts (the "Layer 1" tests in `evals/EVAL_SUITE_PLAN.md`); the agent cases exercise them indirectly.
- `code-researcher` runs offline in its case, so Pass 2 and 3 (code verification online) are not evaluated.
- Most cases grade the deliverable, not the steps. A run that skips an unconditional step and still produces the right file passes (bid-evaluator skipped its spec review and bid-tabulator its resumption log on 2026-10-04, both at 1.00). The three bid cases now carry process graders for the steps those runs skipped (`reads-specs`, `extraction-state`, `no-helper-scripts`, `no-inline-python`, `text-dump-script`, `template-dump-script`); the other cases do not yet, and the bid cases still leave some steps ungraded (subcontract-writer reported skipping its Phase 5 placeholder and per-article checks on 2026-10-05 and passed, because the Python check covers the outcome). When judging a skill's workflow, read the run's final message and trace as well as its score.

## Writing a case

Each case is a folder with `prompt.md` (frontmatter + the prompt), `case.yaml` (the scaffold), `setup.sh`, and `graders/*.md`. Copy an existing case.

The suite's conventions, which every case is expected to follow (they implement §7 of `docs/CM_SKILLS_SOP.md`: 3-5 verifiable assertions, 100% of seeded conflicts surfaced, no fabricated references):

1. **Sanibel documents are the basis.** Real-tier inputs are derived from the downloaded set by `_fixtures/sanibel/make_fixtures.py`; synthetic documents (bids, templates, addenda, submittals) are written against real Sanibel sheets and spec sections. The 4-sheet `sample-project` smoke fixture is the one exception, kept as a sub-$1 install check.
2. **Ground truth is a committed file produced by a script**, not prose: `_fixtures/sanibel/derive_ground_truth.py` for the real documents, a generator plus a defect manifest for synthetic ones.
3. **Deliverables are graded by a Python check** (`harness.yaml` + `checks/*.py`, with `score:` for partial credit) against that ground truth; `llm` graders judge format and behaviour, not facts.
4. **Prompts pin output paths** the skill leaves open, and pre-answer every confirmation gate in `append_system_prompt`.
5. **Tools:** `Read, Write, Edit, Glob, Grep, Bash, Skill`; no subagents.
6. **Limits:** `max_turns` at most 150, `timeout_seconds` at most 2400, budget $3 unless `harness.yaml` raises it.
7. **Fixtures start from bound documents** (so splitting is exercised) or from the pre-split real sections `make_fixtures.py` produces; prepared `.construction/` state is avoided.
8. **Every generated document says it is an eval fixture** and uses invented firms and people.
9. **Eval output is not committed** (`evals/results/` is ignored); results are reported in the PR or the README tables.
10. **Folder names** are the skill name, with `-real` for a real-tier case of a skill that also has a smoke case. See the [plugin eval docs](https://code.claude.com/docs/en/plugin-evals) for grader types; the harness implements `file_exists`, `regex`, `tool_used`, `tool_order` and `llm`, plus `python` checks declared in `harness.yaml`.
