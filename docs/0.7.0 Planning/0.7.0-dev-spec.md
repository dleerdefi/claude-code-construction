# SPEC: 0.7.0, coordinator and partition workers, and the pstack port

**Status:** decisions D1 to D13 confirmed by the user on 2026-10-15. Follows the house style of `docs/specs/revision-history.md`; move there when 0.7.0 starts. The reasoning behind every choice is in `architecture-assessment.md`, beside this file.

**Base:** `main` after PR #28 (`release/0.6.0`) merges. Every path and rule below assumes 0.6.0's layout: findings under `.construction/skills/<skill>/findings/`, AgentCM read from its files only, writes through the API or the outbox, `dev/gate` before every commit.

**Requirement IDs:** `D-*` decisions · `F-*` findings the design relies on · `SR-*` scope router · `WK-*` worker contract · `BC-*` batch checker · `DL-*` decision log · `AG-*` plugin agent · `RE-*` rule → enforcer table · `SOP-*` SOP and guide changes · `PE-*` pe-review (pilot) · `TA-*` tag-audit-and-takeoff · `SL-*` submittal-log-generator · `SV-*` submittal-review · `CK-*` review-check experiment · `HR-*` harness · `G-*` guardrails · `EV-*` evals · `V-*` checks before shipping.

## 0. Decisions (D1 to D13 confirmed 2026-10-15)

- D1. **Execution model:** a skill's coordinator (the session that received the command) spawns **ephemeral workers with the Agent tool, inside the same session.** No skill depends on a second session, on agent teams, or on cross-session messaging.
- D2. **Workers are scoped to a partition and live for one batch.** There are no standing per-discipline or per-scope agents. A worker is never resumed; a failed batch gets a fresh worker with the same brief, once, then a recorded gap.
- D3. **Routing is a script.** Which partitions a task touches comes from `scripts/scope_router.py` reading AgentCM's files (or the flat-file indexes), never from the coordinator's judgment.
- D4. **No router skill in 0.7.0.** Fan-out lives inside the skills that need it.
- D5. **Scope:** shared infrastructure first (§3, §5), then pe-review as the pilot (§4.1), then tag-audit-and-takeoff and submittal-review (§4.2, §4.4). submittal-log-generator is measured, not changed (§4.3). New construction-administration skills are out of scope.
- D6. **Fan-out is on by default in a skill only after its A/B (EV-4) shows the score held and the cost is explained.** Until then it is on above the threshold and the run records what it cost.
- D7. **Workers never message each other, never spawn, never talk to the PE.** Communication is upward only, through files. A cross-partition question is a finding with the `xrefs.tsv` line as evidence; the coordinator routes it.
- D8. **One writer per file.** The coordinator alone writes the issue registry, the submittal log, `corrections.tsv`, any outbox, any API call, the findings folder and the deliverables. A worker writes only under its own folder.
- D9. **pstack items ported:** the worker contract with "gather, don't conclude" (§3.2), gaps as required output (SOP-4), the decision log (§3.4), the rule → enforcer table (§3.6), fresh workers and upward-only communication (D2, D7), the todo-list and reply conventions (SOP-2, SOP-3), a measured prune pass (EV-9), and the review-check experiment (§4.5). Everything else in pstack is rejected for the reasons in the assessment §6.
- D10. **Python only.** `jsonschema` is added to `requirements.txt` for the batch checker; nothing else new.
- D11. **submittal-review keeps its file layout and `check_review.py`.** It adopts the contract text, the decision log and the plugin agent, not the shared folder layout (its two cases are the most expensive in the suite; a layout change would re-spend them for no PE-visible gain).
- D12. **Separate sessions are documented, not built:** one page for developers on using cross-session messaging between an AgentCM session and a skills session, marked advanced, outside every skill.
- D13. **A free-form question outside a skill gets the same workflow through construction-guide,** which loads before any document work: the router runs when the question spans partitions, a lookup is answered from AgentCM's index with no workers, a review or absence question routes to pe-review, and a many-drawing read fans out only after the PE has seen the scope and agreed (§4.6). A single-sheet question never runs the router.

## 2. Where it sits

Nothing changes for the PE. `/construction:pe-review` (and the other two) run as today; above a threshold the skill fans out and says so in its report. The shared pieces:

```
scripts/scope_router.py          which partitions a task touches (SR)
reference/worker-contract.md     the text every worker brief carries (WK)
reference/fan-out.md             the coordinator's side: when, how, thresholds, re-runs (WK-9)
scripts/check_batch.py           scaffold, check and merge worker output (BC)
scripts/decision_log.py          decisions.tsv (DL)
agents/pe-worker.md              the plugin's worker agent (AG)
```

A fan-out run's working data:

```
.construction/skills/<skill>/<run_id>/
  state.yaml            as today, plus fan_out: true|false and the threshold that decided it
  scope.json            scope_router.py output
  decisions.tsv         decision log
  workers/NN/           one folder per batch: brief.md, record.json, findings.json, crops/ (flat-file mode)
  merged.json           check_batch.py merge output, where the skill merges
```

Deliverables are unchanged in shape and place: the same exporters write the same workbook whether or not the run fanned out.

## 3. Shared infrastructure

### 3.1 Scope router (`scripts/scope_router.py`)

- SR-1. **Purpose:** given what a task is about, say which partitions of the document set it touches, which other partitions it reaches through references, and what could not be placed. Deterministic; no model call; unit-tested.
- SR-2. **Inputs:** `--sheets`, `--sections`, `--rooms`, `--tags` (comma lists; any may be empty), `--hops N` (default 1), `--output <scope.json>`. Mode is read from `.construction/project.yaml` as every skill reads it.
- SR-3. **Sources, AgentCM mode:** `INDEX.md` (sheet table: number, title, discipline, text completeness, PDF and page; section table: number, title, division), `xrefs.tsv`, `tags.tsv`. Flat-file mode: `sheet_index.yaml` (sheet-splitter's) and `spec_index.yaml`; there are no references, and the output says `"xrefs": "unavailable"`.
- SR-4. **Partition keys.** A sheet's discipline: `INDEX.md`'s Discipline when it is not `unknown`; otherwise the sheet number's prefix through a new `reference/discipline_prefixes.yaml` (A, S, M, E, P, FP, C, L, G, T, Q, I, FS, …, derived from `reference/drawing_conventions.md`); otherwise the sheet goes to `unplaced` with the reason. A section's partition is its division through `reference/csi_masterformat.yaml`, which also supplies `typical_subs`. The output records which source placed each sheet (`index` or `prefix`).
- SR-5. **Expansion.** For each sheet in scope, every `xrefs.tsv` line from it whose target lies outside the scope's partitions is a `cross_ref` (with `kind`, `how`, `found`, `text`, and the target's partition). With `--hops 1` the referenced sheets are listed under `expanded`, each with the lines that pulled it in; they are not added to `partitions` (the coordinator decides). A `target: discipline` line names the partition by discipline name. A `target: missing` line (not in this project) is reported as `discipline not in set`, never as broken (the roadmap's Sanibel caveat).
- SR-6. **Rooms and tags.** A room or tag in scope adds every sheet `tags.tsv` places it on, and the output says how each occurrence is known (`accepted`, `schedule`, `text`). When `INDEX.md` says the room list is incomplete, the output carries that warning verbatim.
- SR-7. **Output:** `scope.json` with `mode`, `scope`, `partitions[]` (key, kind, label, source, sheets[], sections[], typical_subs[], text status per sheet from INDEX.md), `cross_refs[]`, `expanded`, `unplaced[]`, `warnings[]`, `sources{}`. Example in Appendix B.
- SR-8. **Sizing.** Each partition entry carries counts (sheets, sections, INDEX.md line counts where known) so the coordinator can split a large partition into batches without reading the sheets.
- SR-9. Never writes anything but `--output`. Never reads the database. Exit 0 with warnings for `unplaced`; exit 2 for a missing index.

### 3.2 Worker contract (`reference/worker-contract.md`)

- WK-1. **One text, carried verbatim in every worker brief,** followed by the skill's addendum (`skills/<skill>/references/worker-<task>.md`) and the filled fields. Generalized from submittal-review's `worker-prompt.md`; that file becomes the addendum.
- WK-2. **Brief fields** (shape borrowed from pstack's orchestrate brief, trimmed): `GOAL` one sentence; `MODE` (given, never re-detected); `PARTITION` (key, label, the sheets and sections, from `scope.json`); `FILES` to read, by path; `WRITE` the worker's folder and the files it must produce; `NEVER` (WK-4); `VERIFY` how the coordinator will check (the checker and the schema); `REPORT` one line, counts only; `TIMEBOX` the turn cap. A field the coordinator cannot fill is a batch it has not scoped yet (refuse to spawn).
- WK-3. **What a worker does:** loads `construction-guide` (preloaded, AG-2) and reads `reference/agentcm-mode.md` by path in AgentCM mode; reads `pending.tsv` before trusting a sheet; reads only its partition's files; looks at drawings through `crop.sh` (AgentCM) or rasterizes into its own `crops/` (flat file); cites both sides of every finding; writes `record.json` (every item `done` or `unavailable` with what is missing) and `findings.json` (the skill's schema); replies one line.
- WK-4. **What a worker never does:** write outside its folder; write the issue registry, a log workbook, `corrections.tsv`, an outbox, or call the API; run a script the brief does not list; write a script or inline Python; spawn an agent or message one; ask the user anything; re-detect the mode; conclude across partitions (a cross-partition question is a finding with the `xrefs.tsv` line as evidence, owner `coordinator`); state a code requirement it did not read.
- WK-5. **Gaps are required output.** `record.json` carries `unverifiable[]` (what, and what is missing) and `not_found_in_index[]` (searched where, found nothing). An empty gaps list on a batch of more than a few items is itself flagged by the checker (BC-4).
- WK-6. **The reply is not data.** The coordinator never parses a worker's reply; the files are the result (submittal-log-generator's anti-pattern paragraph, promoted to the contract).
- WK-7. **Model and size:** `sonnet` unless the skill's SKILL.md names another; five to eight items per batch by default; the coordinator spawns all batches in one message and at most eight at once.
- WK-8. **Re-runs:** an incomplete batch (BC-3) is re-run once with the same brief and a fresh worker; a second miss is a gap recorded in `decisions.tsv` and in the report, never silently redone by the coordinator.
- WK-9. **`reference/fan-out.md`** holds the coordinator's side in one page: decide the threshold from `scope.json` counts, write `scope.json` and the briefs, spawn, check, re-run, merge, reconcile cross-partition items, gate, then report. Every fan-out skill's SKILL.md points at it instead of restating it.

### 3.3 Batch checker (`scripts/check_batch.py`)

- BC-1. `scaffold --run-dir D --batch NN --items items.json [--brief brief.md]` writes `workers/NN/record.json` with every item `todo` and copies the brief beside it.
- BC-2. `check --run-dir D --schema <findings schema>`: every batch folder has `record.json` and `findings.json`; every item is `done` or `unavailable`; `findings.json` validates against the schema (`jsonschema`, D10); every finding names an item in the record and both sides of its citation. Prints one line per batch and exits 0 (complete), 1 (incomplete, naming the batches to re-run), 2 (bad input).
- BC-3. **Incomplete** means a missing file, an item still `todo`, or a findings file that does not validate.
- BC-4. A batch of more than four items with empty `unverifiable` and `not_found_in_index` is reported as `suspicious` (exit 0 still; it is for the coordinator to look at, per WK-5).
- BC-5. `merge --run-dir D --output merged.json [--sort key]` concatenates every batch's findings, stable-sorted, with each finding tagged by its batch. Replaces `jq -s 'add'` (F9).
- BC-6. Unit tests in `tests/test_check_batch.py` (a complete run, a missing file, a `todo` item, an invalid finding, an empty-gaps batch).

### 3.4 Decision log (`scripts/decision_log.py`)

- DL-1. `--log <decisions.tsv> --phase P --decision "…" --why "…" --evidence <path or id> --result "…"`: appends one row with an ISO timestamp; writes the header on first use; strips tabs and newlines; prefixes a cell starting with `=`, `+`, `-` or `@` with a quote (pstack's `log.sh`, in Python).
- DL-2. A run that resumes a log another run wrote first adds a `start` row naming the prior rows' timestamp range (pstack's rule, kept so a resumed coordinator is visible).
- DL-3. `--check <decisions.tsv>` validates columns, timestamps and `start` rows; exit 1 on a malformed file. The harness grader uses it (HR-6).
- DL-4. **What gets a row** in a fan-out skill: the mode chosen; the scope computed (evidence `scope.json`); the threshold decision (fan out or not, with the counts); each batch spawned (evidence the brief path) and each batch checked (result); each re-run and each recorded gap; each PE checkpoint and the answer (or `unattended`); the gate result; the report written (evidence the deliverable path). Not every tool call.
- DL-5. The log is working data (`.construction/skills/<skill>/<run_id>/decisions.tsv`), never a deliverable, and is append-only: a wrong call gets a superseding row.
- DL-6. **Resume.** A coordinator that restarts (compaction, a new session) reads `state.yaml` and `decisions.tsv`, re-runs `check_batch.py check`, and re-spawns only the incomplete batches. The spec requires this path to be exercised once by hand before 0.7.0 ships (V-8).

### 3.5 Plugin agent (`agents/pe-worker.md`)

- AG-1. Frontmatter: `name: pe-worker`; a description that says it is spawned only by a skill's coordinator with a brief built on the contract and never to run a whole skill; `tools: Read, Glob, Grep, Bash, Write, Edit` (no `Agent`, no `Skill`, no `SendMessage`: it cannot nest, cannot invoke a user-invoked skill, cannot message); `model: sonnet`; `skills: [construction-guide]`; `maxTurns: 60`.
- AG-2. `skills:` preloads `construction-guide` (model-invocable, so allowed by F3). `agentcm-mode.md` is a reference file, read by path from the brief.
- AG-3. The manifest lists it: `"agents": ["./agents/pe-worker.md"]` in `.claude-plugin/plugin.json`. The folder is the plugin root's `agents/`, distinct from each skill's `agents/openai.yaml` (Codex).
- AG-4. The coordinator spawns it with the Agent tool: `subagent_type: "construction:pe-worker"` (the manifest name, a colon, the agent's name; measured, V-4), `run_in_background: true`, `model` per WK-7, the brief as the prompt. Never with `isolation`, never with `name` (D7). The CLI may start a worker in the background even when the flag is left out, so the coordinator's word about foreground or background is not evidence; the worker's `.meta.json` (`requestShape`) is.
- AG-5. In interactive use a background worker's permission prompts surface in the PE's session (docs). The skill's report says so once at the start of a fan-out ("you may be asked to allow Bash for the workers"); V-6 measures how many prompts a Sonnet worker raises on a real run and whether the plugin should document an allow rule.

### 3.6 Rule → enforcer table (`.claude/CLAUDE.md`)

- RE-1. A table pairing each rule contributors are held to with what enforces it: no inline Python (graders, `dev/gate`?), no writes under `.construction/` outside `skills/` (`dev/check_construction_writes.py`, the harness blocker), no database queries (`dev/check_no_queries.py`, the `no-database-query` grader), 500-line SKILL.md (new `dev/gate` step, RE-3), VERSION = plugin.json (`dev/gate`), workers write only their folder (`check_batch.py`, HR-6), coordinator is the one writer of the registry and outbox (HR-6), decision log present and valid (HR-6), every brief carries the contract (HR-6).

## 4. Per-skill changes

### 4.1 pe-review (pilot)

- PE-1. **Scope step.** After the mode is decided, the skill writes the sheets, sections, rooms and tags the request names and runs `scope_router.py`. With `unplaced` sheets it tells the PE which and continues with the placed ones.
- PE-2. **Threshold:** fan out when `scope.json` has more than one discipline partition or more than 10 sheets in scope (both numbers in SKILL.md, revisited after EV-4). Below it the skill runs as today.
- PE-3. **Batches:** one worker per discipline partition; a partition over 8 sheets splits into batches of up to 8 sheets. Addendum `references/worker-review.md`: per sheet, the red-flag scan, every `xrefs.tsv` line from the sheet cropped with room around it (0.6.0's rule 10), absence findings naming their basis (rule 11), the partition's spec sections read from `specs/`. A findings schema, `references/pe-findings.schema.json`, derived from the finding shape `references/pe-findings.md` already describes (severity, type, priority, status, both sources), so the checker can validate a batch (BC-2); pe-review has no schema file today.
- PE-4. **Cross-partition items.** Every `cross_refs` line in `scope.json` is assigned: the worker that owns the source sheet records what the source shows (crop); the coordinator reads the target (its own crop, or the target partition's worker record when that partition is in scope) and writes the coordination finding itself. No worker writes a finding about another partition's sheet.
- PE-5. **Coordinator:** merges with `check_batch.py merge`, reconciles cross-partition items, applies the coordination matrix across partitions, logs design-team items with `issue_manager.py` (sole writer), writes `coordination_issues.md` and `document_gaps.md` as today, writes the finding with `write_finding.py --skill pe-review`, and reports with the "Could not verify" section (SOP-4) and a one-paragraph fan-out summary (partitions, batches, re-runs, gaps, cost if known).
- PE-6. SKILL.md stays under 100 lines; everything procedural is in `reference/fan-out.md` and the addendum.

### 4.2 tag-audit-and-takeoff

### 4.5 Review-check experiment

- CK-1. After the gate and before the report, in pe-review and submittal-review, the coordinator may spawn one `pe-worker` with `references/review-check.md`: read the merged findings and, for each, open only the cited sources (the crop, the `.tsv` line, the spec line) and mark it `supported`, `unsupported` (the source does not say that) or `citation_not_found`, with the evidence path. It writes `review_check.json` and nothing else.
- CK-2. The coordinator downgrades an `unsupported` finding to OPEN with a decision row, drops a `citation_not_found` finding only after re-reading the source itself, and never promotes anything.
- CK-3. It ships only if EV-8 shows it corrects at least one verdict without losing a true planted finding, in three runs, at a recorded cost. Otherwise the reference file is deleted.

### 4.6 Outside a skill: a free-form question that spans the set (D13)

A PE's commonest input is not a slash command but a question: "where is X", "does the spec require Y", "is the kitchen equipment coordinated with the electrical". Most such questions touch one partition and are answered from the files in a few turns (the `agentcm-mode-construction-guide` case). The ones that span the set fall into three kinds, and only one of them needs workers.

- CG-1. **The rule lives in `skills/construction-guide/SKILL.md`,** the model-invocable guide that loads before any document work, as about ten lines under "Cross-Skill Infrastructure": when a question names more than one discipline, a whole discipline, "the set", or more than 10 sheets, run `scope_router.py` first and read `reference/fan-out.md`. The guide stays under 500 lines (F11).
- CG-2. **Three outcomes, by what the question asks**, and `scope.json` plus the question's wording decide:
  - A **lookup** (where something is, which sheets refer to a detail or a section, which rows a schedule has, who is on a sheet): in AgentCM mode it is one search over `tags.tsv`, `xrefs.tsv`, `schedules/` and `sheets/*.tsv`, whatever the partition count. The index is the fan-out. No worker, ever.
  - A **review or absence question** (what is missing, conflicts, coordination, "check A against B"): that is pe-review's description. pe-review triggers by description and carries the fan-out of §4.1; the guide names it and never fans out a review itself.
  - A **read across many drawings** (flat-file mode; AgentCM sheets marked `partial` or `pending`; a question only crops can answer on many sheets): the coordinator may fan out under the contract, after CG-3.
- CG-3. **Checkpoint before spending.** Inside a skill the PE agreed to the threshold by typing the command. Outside one, the coordinator shows the scope (partitions and sheet count from `scope.json`), what it will do (how many workers, that it takes minutes and costs more than an answer from the index), and asks in one short message before spawning. Unattended (an eval, or the PE said to proceed), it goes and says so in the report.
- CG-4. Everything else is as in a skill: the contract, `pe-worker`, one writer, the decision log and worker folders under `.construction/skills/construction-guide/<run_id>/`, the "Could not verify" section in the answer.
- CG-5. A single-sheet or single-section question never runs the router or a worker; the negative grader in EV-11 holds the line.
- CG-6. Flat-file whole-set questions are where fan-out helps least and the roadmap's per-sheet text index (its prerequisite 3) helps most; the guide says that an AgentCM project answers them from its index, and that is the recommendation, not a workaround.

## 5. Harness changes (`evals/harness/`)

- HR-1. A case opts in with `fan_out: true` in `harness.yaml`; the runner then adds `Agent` to the allowed tools and raises the budget to the case's `budget_usd` (required for such a case). A case without the flag that calls `Agent` fails a new blocker, `unplanned-fan-out`, which is a `tool_used Agent max: 0` on every non-fan-out case. This matters today: the two submittal-review cases grant `Agent`, and any run that spawns a worker is already graded on the worker's calls (F8); their saved traces hold no `Agent` call yet.
- HR-2. The trace is the grading source for worker calls (V-10). The runner keeps `parent_tool_use_id` on every trace entry (today `_block_summary` drops it), so `tool_used`, `regex` on `tool_inputs`, `crops-through-crop-sh`, `no-inline-python` and the writes-outside blocker see a worker's calls with attribution. `forward_subagent_text` stays off: it adds the worker's thinking and text and changes nothing about the tool blocks. `summary.md` gains worker count (distinct parent ids) and worker turns per run. The copied transcripts (HR-5) are the audit and `--regrade` source, not the grading source.
- HR-3. The guard covers workers as it is (V-1): every worker Bash, Write and Edit call reaches the hook, denials take effect, and the worker inherits the session's `allowed_tools` and `permission_mode`. One change: `guard_hook` records the hook input's `agent_id` and `agent_type` on each `guard_log.json` entry, so HR-6's checks can attribute a call. Two limits to remember: a call that fails the tool's own validation (an Edit on a missing file) never reaches the guard and shows only in the trace, and `Read` is not a guarded tool. `ResultMessage.permission_denials` is not a record of worker denials (it was empty for a background worker); the guard log is.
- HR-4. Cost: `total_cost_usd` is the whole run, workers included (V-2). The runner reports `model_usage` per model beside it; when the worker runs on a model the coordinator does not use, that is `worker_cost_usd`. - HR-5. Worker transcripts are copied into the run folder so `--regrade` and an audit can read them: `~/.claude/projects/<sanitized workspace>/<session_id>/subagents/agent-<id>.jsonl` with its `.meta.json` (V-3; the sanitized name replaces every non-alphanumeric character of the workspace path with `-`; `session_id` is `ResultMessage.session_id`; `claude_agent_sdk.list_subagents(session_id, directory=workspace)` lists them). - HR-6. New shared checks in `evals/plugin/_checks/`: `worker_containment.py` (every file a worker's Write or Bash created is under `workers/NN/` or `.construction/crops/`); `single_writer.py` (the issue registry, outbox, `corrections.tsv` and every deliverable were written by coordinator calls only); `decision_log.py` (`decisions.tsv` exists, `--check` passes, one row per batch spawned and per gate); `brief_carries_contract.py` (every Agent prompt contains the contract's marker line); `fan_out_threshold.py` (no `Agent` call below the threshold, at least one above). Each reads worker calls from the trace (with `parent_tool_use_id`, HR-2) and worker denials from the guard log (with `agent_id`, HR-3); a validation-failed call is in the trace only, and a worker's `Read` is in the trace only.
- HR-7. **A/B:** `harness.yaml` may declare `variants:`; each variant is the same case with an extra `append_system_prompt` line, and the runner reports the variants side by side (score, turns, cost, wall time, workers). The no-fan-out arm appends "Do not use sub-agents; do everything in this session." No skill change is needed for the switch.
- HR-8. `docs/RUNNING_EVALS.md` and the harness README describe `fan_out`, `variants`, the worker lines in `summary.md`, and the cost of each fan-out case (pe-review-set, the tag-audit multi-sheet case, the two submittal-review cases).

## 6. Guardrails

- G-1. One writer per file; the coordinator is the only writer of the issue registry, logs, `corrections.tsv`, outboxes, API calls, findings and deliverables (D8).
- G-2. Workers never spawn, message, resume or ask (D2, D7). A worker's tools omit `Agent`, `Skill` and `SendMessage`.
- G-3. Every brief carries the contract verbatim and stands alone; a brief with an unfilled field is not sent.
- G-4. No fan-out below the skill's threshold; the deliverable has the same shape and place with or without fan-out.
- G-5. A worker's reply is never parsed; the files are the result.
- G-6. A failed batch is re-run once, fresh; then it is a gap in the log and the report, never quietly redone.
- G-7. The PE's checkpoints stay in the coordinator; no worker interacts with the user.
- G-8. Fan-out changes no mode rule: files only, no database, `crop.sh` for drawings, writes through the API or the outbox, nothing under `.construction/` outside `skills/` and `crops/`.
- G-9. Every number a fan-out report gives (sheets, findings, gaps, cost) comes from `scope.json`, the merged files and the log, never from memory.
